## 1. 목표와 성공 기준

iOS SwiftUI와 Android Jetpack Compose에서 로그인 없이도 선택한 여행의 기록·준비 정보를 입력하고, 앱을 종료한 뒤 다시 열어도 같은 여행에 보존한다. 지도 키가 없거나 네트워크가 끊겨도 이 화면은 로컬 데이터를 사용할 수 있어야 한다.

성공 기준:

1. `더보기`에서 현재 여행을 선택하거나 여행이 없을 때 명확한 선택 안내를 볼 수 있다.
2. 여행 기록을 날짜·제목·내용·일정 장소로 저장하고 수정·삭제할 수 있다.
3. 기록에 사진 한 장을 추가하고 사진 선택 취소·권한 거절·용량 초과를 안전하게 처리한다.
4. 준비 체크리스트를 항목별로 추가·완료·삭제할 수 있다.
5. 출발지·도착지·항공편·숙소명·숙소 주소를 저장하고 다시 편집할 수 있다.
6. 저장 실패 시 성공 문구를 표시하지 않고 입력 중인 내용과 기존 원본을 보존한다.
7. iOS와 Android가 같은 여행 JSON 필드와 동일한 식별·정렬 규칙을 사용한다.
8. 기존 필드와 네이티브가 아직 편집하지 않는 미지 필드를 저장 시 삭제하지 않는다.

## 3. 데이터 계약

기준은 현재 웹의 여행 JSON이다. 네이티브 화면은 아래 필드를 읽고 쓰며, 저장되지 않은 다른 키는 원본 객체에 남긴다.

### `travelDetails`

```json
{
  "departure": "인천공항",
  "arrival": "나리타공항",
  "flightNumber": "KE703",
  "stayName": "도쿄 호텔",
  "stayAddress": "도쿄도 신주쿠구"
}
```

모든 값은 문자열이며, 빈 값도 유효한 값으로 저장한다. 입력 화면은 한 번의 원자적 여행 업데이트로 다섯 필드를 함께 저장한다.

### `checklist`

기존 웹 배열의 항목을 보존하며 네이티브가 생성하는 최소 형식은 다음과 같다.

```json
{
  "id": "check-uuid",
  "label": "여권 확인",
  "checked": false
}
```

실제 웹 `src/App.jsx`의 추가·토글·표시와 네이티브 기본값은 모두 `checked`를 사용한다. `completed`라는 새 필드는 만들지 않는다. 새 항목은 UUID 문자열 ID, 공백을 제거한 `label`, boolean `checked`를 가진다. 기존 항목의 숫자/문자 ID와 추가 필드는 원형을 보존한다.

배열 전체를 오래된 화면 상태로 덮어쓰지 않고 항목 추가·완료 설정·삭제 명령을 저장소에 전달한다. 정상 항목은 타입을 구분한 ID와 편집 시작 시 원본 행으로 대상을 확인한다. ID가 없거나 중복된 항목은 화면에 보존하되 `배열 인덱스 + 편집 시작 시 배열 전체 스냅샷`을 검증한 경우에만 해당 행을 변경한다. 배열이 달라지면 다시 불러오기 안내를 표시한다. 인덱스만 안정적인 영구 식별자로 취급하지 않는다. 읽기만으로 ID를 생성하거나 원본을 변경하지 않는다.

### `journalEntries`

```json
{
  "id": "journal-uuid",
  "date": "2026-09-22",
  "title": "첫날의 저녁",
  "body": "도착 후 시장을 둘러봤다.",
  "imageDataUrl": "",
  "imageFileName": "",
  "place": {
    "key": "1:place-id",
    "day": 1,
    "id": "place-id",
    "name": "도쿄역",
    "address": "도쿄"
  },
  "createdAt": 1780000000000,
  "updatedAt": 1780000000000
}
```

기존 웹 `imageDataUrl`은 원본 그대로 보존하고 실제로 디코딩할 수 있는 사진만 표시한다. 네이티브에서 새로 선택한 사진은 앱 전용 파일 저장소에 보관하고, 로컬 JSON의 `imageFileName`에는 앱이 생성한 참조만 기록한다. 기존 사진을 교체할 때도 새 UUID 파일에 기록한다. DB 저장 전에 원래 사진 파일을 덮어쓰거나 삭제하지 않는다. DB 커밋 뒤에만 새 참조가 활성화되며, 실패 시 기존 기록·사진과 편집 초안을 유지한다.

외부에서 가져온 여행/기록 ID를 파일 경로에 직접 이어 붙이지 않는다. 여행 ID의 SHA-256 디렉터리와 앱에서 생성한 UUID 파일명을 사용하고 루트 밖 경로·심볼릭 링크를 거부한다. 가져온 JSON의 `imageFileName`을 로컬 파일 접근 권한으로 믿지 않는다.

JSON 백업 시에는 로컬 사진을 읽어 내보낼 사본의 `imageDataUrl`에 MIME과 base64 바이트를 넣고 `imageFileName`은 제거한다. 원본 DB는 변경하지 않는다. 가져오기는 `imageDataUrl`을 보존해 다른 기기에서도 표시하고, 외부 로컬 참조는 경고와 함께 제거하되 기존 가져오기 영수증의 원본 바이트는 유지한다. 사진 누락/읽기 실패가 있으면 성공한 백업으로 표시하지 않는다. 최종 UTF-8 JSON은 현재 `TripBackup.maxBytes`인 20 MiB 이하여야 한다. base64 증가량도 계산하고, 초과 시 사진을 조용히 빼지 않고 내보내기 실패와 원본 보존을 안내한다.

날짜는 `YYYY-MM-DD` 날짜 전용 문자열로 저장하며 기기 시간대 변경으로 기록 날짜가 바뀌지 않게 한다. 새 기록은 유효한 날짜 및 제목·본문·유효한 사진 중 하나가 필요하다. 기존 빈 날짜/긴 글은 읽기만으로 수정하지 않는다. 제목 80자·본문 2000자의 웹 입력 제한을 UTF-16 길이로 맞추되, 기존 초과 값은 변경하지 않는 한 보존한다.

목록은 유효한 날짜 오름차순(날짜 없음/잘못된 날짜는 뒤), `createdAt` 오름차순, ID 순으로 표시한다. 기존 웹의 ID 비교는 `localeCompare`이므로 다양한 문자열 ID가 모든 OS에서 정확히 같은 최종 순서를 가진다고 단정하지 않는다. UUID와 일반 ASCII ID는 공통 fixture로 맞추고, 그 외 ID 비교와 동률의 원본 순서 유지도 명시적으로 테스트한다. 정렬은 표시용 사본에만 적용한다.

편집 시 `createdAt`과 미지 필드는 유지하고 `updatedAt`만 증가시킨다. 항목 대상 검증은 체크리스트와 같다. 새 항목 저장은 초안의 operation ID를 재사용해 재시도 중복을 막는다. 장소 연결은 일정의 원본 ID 타입을 내부 식별자로 유지하고, 웹 표시용 `place.key/id`와 구분한다. 삭제되거나 이동한 장소의 기존 스냅샷은 그대로 표시하고 사용자가 해제를 선택할 때만 제거한다. 새 Google 검색 결과의 일시적 좌표/주소는 영구 기록으로 복제하지 않는다.

## 4. 화면·이동 설계

### 공통 진입

`더보기`의 첫 영역에 현재 여행 요약과 다음 메뉴를 표시한다.

- 여행 기록
- 여행 준비
- 항공·숙소 정보
- 여행 JSON 백업

여행 목록이 있지만 활성 여행이 없으면 더보기에서 명시적으로 대상을 선택한다. 여행이 하나도 없을 때는 `내 여행에서 여행을 먼저 만들어 주세요`와 이동 버튼을 표시한다. 기존 JSON 가져오기 메뉴는 여행이 없어도 사용 가능하다. 로딩/읽기 실패를 빈 목록으로 표시하지 않는다.

각 화면은 `tripID`만 경로로 전달한다. SwiftUI는 더보기의 `NavigationStack`에 실제 목적지를 등록한다. Compose는 URL 인코딩한 여행 ID와 더보기 하위 navigation graph를 사용해 상세에서도 더보기 탭 선택 표시와 탭별 복귀가 유지되게 한다. 사진 선택기 응답은 `(tripID, draftID, selectionID)`가 일치할 때만 반영한다.

### 여행 기록

- 상단: 여행명, 기간, 기록 개수
- 입력: 기록 날짜, 제목, 내용, 일정 장소 선택, 사진 추가
- 목록: 날짜별 섹션, 제목/본문 요약, 연결 장소, 사진 미리보기
- 동작: 새 기록, 수정, 삭제 확인
- 저장 중에는 중복 제출을 막고, 저장 완료 후에만 입력 화면을 초기화한다.

### 여행 준비

- 체크리스트 항목 목록
- 항목 추가 입력
- 완료 토글
- 삭제 확인
- 기존 체크리스트 항목의 알 수 없는 필드는 유지

### 항공·숙소 정보

- 출발지, 도착지, 항공편, 숙소명, 숙소 주소 폼
- 저장 버튼과 마지막 저장 상태
- 여행 상세 화면에서 다시 진입해도 서버/지도 상태와 무관하게 로컬 값 표시

## 5. 저장소 인터페이스

양 플랫폼 저장소는 동일한 의미의 원자적 메서드를 제공한다. 아래 이름은 추가할 계획이며 현재 존재하는 API로 취급하지 않는다. 기존 iOS 저장소는 `final class TripRepository`이고 별도 저장소 protocol은 없다.

### Swift

`TripRepository`에 다음 메서드를 추가한다.

```swift
func applyMemoryChange(tripID: String, change: MemoryChange) throws -> TripDocument
```

`MemoryChange`는 `setTravelDetails`, `addChecklist`, `setChecklistChecked`, `removeChecklist`, `addJournal`, `editJournal`, `removeJournal`을 가진 enum이다. 변경된 상세 필드만 전달하며 기존 필드 값도 함께 검증한다. 행 수정/삭제에는 편집 시작 시 원본 행(레거시는 배열 스냅샷도)을 포함해 동시 변경을 탐지한다. `TripMemory.apply` 순수 함수가 최신 여행에 명령을 적용하고 저장소는 기존 트랜잭션에서 저장·재읽기를 수행한다. 실제 디스크 재열기 검증도 별도로 수행한다.

### Kotlin

`TripRepository`에 같은 의미의 메서드를 추가한다.

```kotlin
suspend fun applyMemoryChange(tripID: String, change: MemoryChange): TripDocument
```

Kotlin `MemoryChange` sealed interface는 Swift enum과 동일한 명령/검증을 사용한다. Room 트랜잭션에서 최신 `TripEntity`를 읽고 실제 변경에만 `updatedAt`을 증가시키며 저장 후 JSON 동등성을 확인한다. 사진 저장은 `Context.filesDir/trip-media/<tripID의 SHA-256>/<새 UUID>` 경계를 사용한다. 기존 `TripViewModelTest`와 `TripBackupViewModelTest`의 repository test double도 새 인터페이스에 맞춘다.

## 6. 오류·권한·수명주기 규칙

- 사진 선택 취소: 입력 화면을 유지하고 오류 문구를 표시하지 않는다.
- 시스템 선택기는 선택된 사진만 읽는다. iOS `PhotosPicker`와 Android `PickVisualMedia`를 사용하며, Android는 제공되지 않는 기기에서 Activity 라이브러리의 파일 선택 fallback을 따른다. 전체 사진 라이브러리 권한을 선요청하지 않는다. 제공자 읽기 거절·클라우드 사진 다운로드 실패 시 재시도/사진 없이 계속하기를 제공한다.
- 새 사진의 읽기 한도는 `2.5 * 1024 * 1024 = 2,621,440 bytes`이며 한도+1까지만 스트림을 읽는다. MIME뿐 아니라 실제 디코더로 형식/크기를 확인하고 화면용 축소 디코딩을 수행한다. JPEG/PNG 또는 변환 가능한 HEIF를 처리하며 웹에 내보낼 신규 사진은 JPEG/PNG로 저장한다. 변환 후에도 같은 크기 한도를 적용한다. 초과/읽기 실패 시 새 선택은 적용하지 않고 이전 사진과 입력 내용을 유지하며 사진 없이 저장할 수 있게 한다.
- 저장 실패: 기존 여행 원본을 그대로 두고 “저장됨” 상태를 만들지 않는다.
- 미저장 폼은 `(tripID, 화면 종류, draftID)`로 구분한 앱 전용 초안 파일에 변경 시점부터 저장한다. DB 원본과 분리하고 텍스트·선택 장소·새 기록 operation ID·임시 사진 참조를 보존한다. `SavedStateHandle`/`SceneStorage`에는 작은 식별자만 두며 사진 바이트는 넣지 않는다. 저장 성공/명시적 버리기 후에만 초안을 삭제한다. 강제 종료에선 background 콜백이 생략될 수 있으므로 해당 콜백에만 의존하지 않는다.
- 기록 삭제와 체크 항목 삭제는 확인 절차를 거친다.
- 여행 삭제 후 화면이 남아 있으면 목록으로 돌아간다. 파일 정리는 DB 커밋 이후, 그리고 시작 시 전체 여행·진행 중 초안·내보내기 작업의 참조 집합을 확보한 상태에서 직렬 실행한다. 읽기 실패 시 정리를 생략하고, 다른 여행/초안에서 참조 중인 사진은 제거하지 않는다. 정리 실패는 저장/삭제 완료와 별도 상태로 기록한다.
- 로그인·동기화는 이번 범위에 없으므로 로컬 저장 완료를 서버 동기화 완료로 표시하지 않는다.

## 7. 테스트 전략

### 공통 계약

- `travelDetails` 저장 시 다른 여행 필드와 미지 필드가 유지되는지 확인
- 체크리스트 토글·삭제가 기존 항목의 확장 필드를 보존하는지 확인
- 기록 추가·수정·삭제가 정렬과 `createdAt` 보존을 만족하는지 확인
- 동일한 fixture로 Swift/Kotlin JSON 필드 결과를 비교
- 사진 파일 저장 실패 시 JSON 저장이 발생하지 않는지 확인

### iOS

- NativeCore 단위 테스트: 저장소 원자성, 날짜 정렬, 기존 필드 보존, 유효성 검사
- SwiftUI UI 테스트: 더보기→기록 진입, 기록 저장·수정·삭제, 체크 토글, 정보 저장
- 사진 선택기 취소·권한 거절은 실제 시스템 UI 의존 테스트와 순수 저장소 테스트를 분리

### Android

- JVM 테스트: 순수 명령 적용·검증, 항목별 변경, ID 충돌, 정렬, ViewModel 초안/실패 처리
- Android instrumented 테스트: 실제 Room 저장·재열기, 트랜잭션 rollback, 파일 저장·읽기 실패
- Compose UI 테스트: 더보기→기록/준비/정보 진입, 저장·삭제 확인, 뒤로가기 경계
- API 36 에뮬레이터에서 앱 강제 종료 후 기록·체크·정보 재복원

### 회귀

- 웹 테스트와 기존 지도 키 없는 네이티브 테스트를 실행한다.
- iOS/Android 백업 파일에서 기록·체크·여행 정보가 왕복되는지 확인한다.
- `npm run native:security`, 웹 빌드, Swift 테스트, Android JVM/빌드/lint를 모두 통과해야 한다.

## 8. 구현 단계

1. 공통 fixture와 Swift/Kotlin 저장소 실패 테스트를 추가한다.
2. 두 저장소에 원자적 `applyMemoryChange`와 사진·초안 저장을 구현한다.
3. 사진을 포함한 JSON 내보내기/가져오기와 초안 보존을 연결해 데이터 이전 경계를 먼저 검증한다.
4. iOS 화면과 `더보기` 진입·여행 선택·사진 선택기를 함께 구현한다.
5. Android 화면과 `더보기` 하위 내비게이션·여행 선택·사진 선택기를 함께 구현한다.
6. 양 플랫폼 UI/재실행 검증, 웹·보안·빌드 회귀 검증을 실행한다.
7. 파일 공유 5-B로 넘어가기 전에 사진 파일 정리와 백업 호환성 결과를 기록한다.

## 9. 외부 의존성 및 리스크

- 지도 키는 이 기능의 저장·기록 화면에 필요하지 않으며, 실제 지도 검증 보류 상태를 변경하지 않는다.
- 사진 선택기 API는 iOS 16과 Android API 26을 지원해야 한다. Android Activity 라이브러리의 Photo Picker fallback을 사용하고, 하위 API 기기에서도 실제로 검증한다.
- 기존 웹 데이터에 `imageDataUrl`이 큰 경우 네이티브 파일 저장으로 즉시 변환하지 않고 원본을 보존한다. 변환 도구는 5-B 이후 별도 결정한다.
- `checklist`의 실제 웹 계약은 `id/label/checked`로 확인했다. 알 수 없는 필드는 항목 단위 변경에서도 보존한다.
- 다른 기기 이전은 사진 바이트가 포함된 JSON으로 검증한다. 로컬 참조만 저장된 백업을 정상 복원 가능한 파일로 표시하지 않는다.

## 10. 검토 근거

- `src/App.jsx:3808` 및 `ios/NativeCore/Sources/NativeCore/Resources/web-defaults.json:203`: `checked` 사용.
- `src/travelMemory.js:81` 및 `src/TravelMemoryPanel.jsx:348`: 웹은 `imageDataUrl`로 사진을 표시하며 `imageFileName`은 처리하지 않음.
- 양 플랫폼 `TripBackup`은 현재 JSON 직렬화만 수행하고 사진 파일을 포함하지 않으며 가져오기 한도는 20 MiB임.
- [Apple PhotosPicker](https://developer.apple.com/documentation/photosui/photospicker), [Android Photo Picker](https://developer.android.com/training/data-storage/shared/photo-picker): 시스템 사진 선택기 사용 근거.
- 실제 배포·사진 선택기·파일 복원 동작은 구현 후 검증 항목이며, 이번 문서 검토가 동작 검증을 대체하지 않는다.
