## 1. 목표와 성공 기준

현재 구현한 여행 기능을 iPhone과 Android에서 일반 앱처럼 사용한다. 이전에 요청한 Swift·Kotlin 방식을 따르며, 앱의 주 화면·하단 메뉴·일정 편집·지출 입력·정산은 네이티브 화면으로 구현한다. 실행할 때 운영 웹페이지를 내려받아야 본문이 나타나는 구조를 해소한다.

로그인하지 않아도 여행을 만들고 수정할 수 있으며, 앱을 강제 종료하거나 인터넷을 끈 뒤 다시 실행해도 저장한 여행·지출을 읽는다. 로그인한 사용자는 기존 웹과 동일한 계정 및 데이터를 사용한다. 지도 검색·서버 동기화처럼 네트워크가 필요한 기능은 연결 상태에 따라 안내한다.

완료 판단은 양쪽 앱에서 실제 사용 흐름과 저장·이전·동기화를 검증했을 때 한다. 하단 메뉴만 네이티브로 바꾸거나 네이티브 시작 화면만 만든 상태를 전체 전환 완료로 취급하지 않는다.

## 3. 접근 방식과 선택

1. **SwiftUI + Kotlin/Jetpack Compose:** 이전 사용자의 언어 선택과 이번 네이티브 전환 목적에 맞는 권장안. 두 플랫폼 화면·업무 로직을 각각 관리하되, JSON 계약과 공통 테스트 입력으로 결과를 맞춘다.
2. **React Native:** WebView 없이 네이티브 UI를 만드는 대안이지만 Swift·Kotlin 중심이라는 기존 방향과 다르다. 기존 Expo 코드의 데이터 불일치도 해결해야 한다.
3. **WebView 본문 + 네이티브 메뉴:** 이식량은 적지만 주 기능의 웹페이지 의존성이 남아 이번 최종 목표에 맞지 않는다.

권장안은 1번이다. 구조를 크게 바꾸는 작업이므로 기능 묶음별로 이식하고 검증한다. 네이티브 구현 중에도 기존 웹과 서버 계약은 유지한다.

## 4. 구현 구조

| 역할 | iOS | Android |
| --- | --- | --- |
| 화면·폼·하단 메뉴 | SwiftUI, TabView, NavigationStack | Kotlin, Jetpack Compose, Navigation Compose |
| 기기 내 영구 저장 | Core Data의 SQLite 저장소 | Room의 SQLite 저장소 |
| 지도·검색 | Google Maps SDK 및 Places SDK | Google Maps SDK 및 Places SDK |
| 인증·동기화 | 네이티브 인증 저장소와 HTTPS API 어댑터 | 네이티브 인증 저장소와 HTTPS API 어댑터 |
| 사진·파일·공유 | 시스템 사진/파일 선택기 및 공유 화면 | 시스템 Photo Picker/파일 선택기 및 공유 인텐트 |

현재 iOS 16 지원을 유지하기 위해 저장소는 Core Data를 선택한다. SDK 의존성은 해당 지원 범위에 맞는 조합을 빌드 단계에서 고정한다. 최신 SDK가 지원 OS 상향을 요구하면 그 변경을 별도로 검토하고 조용히 적용하지 않는다.

플랫폼 내부는 `화면 → 화면 상태 → 업무 로직 → 저장소 → 로컬 DB/서버 어댑터`로 나눈다. 화면은 로컬 DB에서 읽고, 변경을 로컬에 기록한 뒤 동기화 작업을 예약한다. 웹 URL 로드나 DOM·React 이벤트를 앱 내비게이션 수단으로 사용하지 않는다.

화면 이동에는 여행 ID·탭·선택한 일차 등 직렬화 가능한 값만 전달한다. 버튼·뷰·지도 객체를 저장 상태에 넣지 않는다. 로그인·외부 링크에 쓰는 시스템 인증 브라우저는 업무 화면을 웹뷰로 만드는 것과 구분한다.

공식 참고: [Apple TabView](https://developer.apple.com/documentation/swiftui/tabview), [Apple NavigationStack](https://developer.apple.com/documentation/swiftui/navigationstack), [Core Data](https://developer.apple.com/documentation/coredata), [Android Navigation](https://developer.android.com/guide/navigation), [Room](https://developer.android.com/training/data-storage/room).

| 하단 메뉴 | 기본 화면 | 진입·복귀 규칙 |
| --- | --- | --- |
| 내 여행 | 여행 목록 및 선택한 여행의 일정 | 새 여행 생성 후 상세로 이동. 기존 지도/여행 영역의 자유 분할 기능을 네이티브 컨테이너로 이식한다. |
| 지도 | 네이티브 지도 전체 영역 | 검색·현재 위치·저장 장소 표시. 장소 추가 시 대상 여행과 일차를 명시한다. |
| 저장 | 즐겨찾기 목록 | 세로 스크롤, 검색, 여행 일정에 추가, 지도에서 보기. |
| 지출 | 선택한 여행의 지출 목록·합계·추가 | 여행 미선택 시 여행 선택 화면을 표시한다. 여행 선택 없이 다른 여행에 기록하지 않는다. |
| 더보기 | 여행 기록·준비·데이터·계정·지원 | 여행별 기능은 대상 여행 표시 또는 여행 선택 안내를 제공하고, 메뉴가 이유 없이 사라지지 않게 한다. |

공통 규칙:

- 최초 실행은 로그인 요구 없이 내 여행으로 진입한다. 재실행은 유효한 마지막 탭·여행·스크롤 위치를 복원하며 삭제된 여행은 목록으로 돌린다.
- 탭마다 이동 이력을 보존한다. Android 뒤로 가기는 열린 편집창 → 상세 화면 → 탭 루트 순으로 처리하고 iOS는 시스템 뒤로 가기를 사용한다.
- 지도와 일정의 분할은 실제 두 레이아웃 영역으로 구성한다. 손잡이에서 시작한 드래그만 영역 크기를 조절하고 목록 안의 제스처는 스크롤한다.
- 지도 전체·목록 전체로 확장할 때도 복원용 조작은 남긴다. 지도 위에 목록을 크게 덮는 방식으로 분할을 대체하지 않는다.
- 하단 메뉴·키보드·시스템 안전 영역의 공간을 한 번만 계산한다. 저장 상태는 작게 표시하며 콘텐츠 높이를 차지하는 빈 패널을 만들지 않는다.
- 파스텔 앱 아이콘과 현재 브랜드 표시 자산을 재사용한다. 웹의 작은 글자와 고정 픽셀값을 그대로 복사하지 않고 시스템 글자 크기·터치 영역에 맞춘다.
- 태블릿 가로에서는 넓은 화면에 맞는 좌우 영역을 적용하고, 세로에서는 세로 분할을 제공한다. 웹 데스크톱 화면은 현재 방식으로 계속 제공한다.

## 7. 데이터 계약과 기존 데이터 이전

기준은 현재 웹의 실제 구조다. 여행의 `itinerary`는 `[{ day, items }]` 형태이며 예전 Expo의 평탄한 배열을 기준으로 삼지 않는다. `reserveItems`, `budgetSettings`, `expenses`, `settlementParticipants`, `checklist`, `travelDetails`, `journalEntries`, `reminders`, 날짜와 ID를 보존한다. 앱이 아직 편집하지 않는 필드도 왕복 동기화에서 소실되지 않도록 원본 JSON 확장 필드를 보관한다.

금액 계산은 통화별 최소 단위와 반올림 정책을 명시한다. 현재 정산의 원화 정수 반올림, 참여자 순서에 따른 나머지 배분, 결제자 포함 규칙을 공통 예제로 고정한다. Swift와 Kotlin 이식본은 같은 입력에 같은 결과를 반환해야 한다. 날짜는 여행 날짜와 시각을 구분해 시간대 변경으로 일차가 바뀌지 않도록 한다.

이전 경로는 세 가지다.

1. **기존 계정:** 현재 웹이 쓰는 `user_state`의 `user_id`, `key`, `value` 계약과 여행/즐겨찾기 키를 사용한다. 네이티브 로컬 데이터와 비교한 뒤 합치고, 서버에서 내려받았다는 이유만으로 로컬을 덮어쓰지 않는다.
2. **기존 WebView 앱의 비로그인 데이터:** 업데이트 전에 같은 앱 저장 영역과 운영 원점의 데이터를 백업·추출하는 이행 경로를 검증한다. 한 번만 실행하는 제한된 이전용 WebView가 필요할 수 있으며 이는 일반 앱 화면에 사용하지 않는다. 추출 실패 시 성공으로 표시하거나 기존 저장소를 지우지 않는다.
3. **Safari/Chrome에만 있는 비로그인 데이터:** 새 앱에서 브라우저 저장소를 직접 읽는다고 가정하지 않는다. 기존 웹에서 로그인해 동기화하거나 JSON 백업을 파일로 가져온다. 현재 여행별 백업에는 전역 즐겨찾기가 포함되지 않으므로, 전체 이전에는 즐겨찾기·환경 설정을 함께 내보내는 명시적인 이전 패키지가 필요하다.

이전은 원본 보존 → 해석/필드 검사 → 가져올 내용 미리보기 → DB 트랜잭션 저장 → 재읽기 비교 → 완료 기록 순서로 수행한다. 동일한 이전 패키지를 반복 실행해도 중복 여행을 만들지 않도록 원본 ID와 이전 이력을 사용한다. 사용자가 의도적으로 여행을 복제하는 가져오기와 데이터 이전을 구분한다. 공유 관리 토큰은 일반 백업에 내보내지 않는다.

로컬 저장 완료와 서버 동기화 완료를 구분한다. DB 저장 실패에는 ‘저장됨’을 표시하지 않는다. 로그아웃 후 다른 계정으로 로그인할 때 이전 계정의 데이터가 자동 업로드되지 않도록 계정별 저장 영역을 구분한다.

현재 서버는 여행 배열을 저장하는 구조이므로 삭제/동시 편집을 안전하게 병합하는 계약 검증이 필요하다. 충돌하면 양쪽 원본을 보존하고 복구 가능한 사본으로 처리한다. 여러 클라이언트가 동시에 쓰는 동안 단순 최신 시간 비교로 데이터 보존이 보장된다고 주장하지 않는다. 서버의 원자적 비교·갱신 및 삭제 이력 적용은 웹 호환 검증을 포함한 동기화 단계에서 다룬다.

## 8. 지도·사진·네트워크

기존 Google 기반 장소 경험을 유지하는 것을 기본안으로 한다. 웹용 키의 제한을 풀어 공유하지 않고 iOS 번들 ID, Android 패키지·서명 인증서에 맞게 별도 키를 설정한다. API 활성화와 키 준비 전에도 앱 메뉴·일정·지출·수동 장소 입력은 동작해야 한다. 관련 설정의 근거는 [Google Maps 키 보안 안내](https://developers.google.com/maps/api-security-best-practices)다.

앱 DB를 오프라인으로 읽는 기능과 지도 타일/장소 검색의 오프라인 제공은 구분한다. 지도 타일이나 검색 결과의 무제한 저장을 전제하지 않는다. 키 누락·권한 거절·네트워크 오류가 전체 앱을 오류 페이지로 바꾸지 않게 한다.

사진은 앱 파일 저장소에 보관하고 DB에서 참조한다. 기존 `imageDataUrl`을 이전할 때 형식·용량을 검증하고 원본을 보존한다. 서버에 사진 파일을 별도 보관하는 확장은 기존 웹이 읽는 형식 및 접근 권한과 함께 검증한다. 검증 전에는 기존 형식의 동기화를 보존하며 네이티브 파일 경로를 서버에 그대로 올리지 않는다.

서버 설정·인증·공유 어댑터는 브라우저 전역 변수나 브리지에 의존하지 않는다. 기존 `/api/shared-trips`, `/api/account` 호출에 필요한 HTTP 메서드·토큰·원점 검증을 네이티브 요청과 대조한다. 서버 비밀키는 앱에 포함하지 않는다.

## 9. 순서와 단계별 완료 기준

| 단계 | 구체적인 산출물 | 다음 단계로 넘어가는 기준 |
| --- | --- | --- |
| 1. 앱 기반·저장 | SwiftUI/Compose 진입점, 5개 탭, 여행 생성/목록/편집, 로컬 DB, JSON 계약 예제 | 두 시뮬레이터에서 웹 본문 로드 없이 실행, 여행 생성 후 강제 종료·오프라인 재실행해 보존 |
| 2. 일정·이전 | 일차·예비 목록·순서·시간 편집, 백업 가져오기/내보내기, 기존 데이터 이전 모듈 | 웹 샘플과 구형 데이터 왕복, 반복 이전·중간 종료·잘못된 파일에서 원본 보존 |
| 3. 지도·분할·저장 | 네이티브 지도/검색/현재 위치/마커, 즐겨찾기, 자유 크기 분할 | 지도 이동 중 좌표 안정, 분할과 목록 스크롤 구분, 키·권한 실패 시 나머지 기능 동작 |
| 4. 지출·정산 | 지출 탭 본문, 예산·통화·현금 지갑·참여자 정산 | 기존 웹과 동일 예제 결과, 금액 총합·통화·삭제 검증 및 오프라인 저장 |
| 5. 기록·준비·파일 | 사진/여행 기록, 체크리스트, 항공/숙소, JSON·CSV·ICS·이미지 공유 | 두 OS 파일 선택·공유·권한 취소와 재실행 후 기록 보존 |
| 6. 서버·계정·전환 | 계정별 동기화, 공유 여행, 계정 삭제, 실제 업데이트 데이터 이전 | 웹/iOS/Android 상호 편집·충돌·삭제 검증, 기존 설치 업데이트 보존, 핵심 화면에 WebView 미사용 |

단계 1만 끝난 앱은 전체 기능 이식 완료가 아니다. 개발 중인 화면은 개발 빌드에서 상태를 명확히 하고, 기능이 없는 메뉴를 완성 기능처럼 출시하지 않는다. 원격 서버·지도 키·스토어 계정 연동은 준비 상태를 확인한 뒤 수행한다. 이전에 보류한 개발자 계정 결제는 이번 작업에서 진행하지 않는다.

## 10. 파일 구성과 검증 범위

기존 `ios/`와 `android/` 안에 `Native/App`, `Native/Domain`, `Native/Data`, `Native/Features`, `Native/Migration`에 해당하는 구조를 추가한다. 공통 JSON 예제는 `contracts/native/fixtures/`에 두고 실행 가능한 기대 결과와 함께 관리한다. 기존 앱 식별자·서명키·딥 링크는 배포 전환까지 유지한다.

개발 중에는 명시적인 네이티브 미리보기 빌드를 제공해 기존 WebView 앱을 갑자기 교체하지 않는다. 별도 미리보기 설치는 기존 앱의 저장 공간을 공유하지 않는다는 점을 테스트에서 구분한다. 실제 기존 앱 업데이트 검증은 같은 식별자로 설치한 테스트 데이터가 있는 앱에서 수행한다.

필수 검증은 단순 소스 문자열 검사가 아니라 저장·계산·화면 이동의 실제 동작이다. 여행 생성→장소 추가→지출 입력→앱 종료→재실행을 두 플랫폼에서 수행한다. 정산 계산은 공통 입력/기대값, 저장은 실제 DB 재열기, 이전은 실패 주입과 재시도, UI는 키보드·큰 글자·회전·뒤로 가기·탭 복귀를 확인한다. 기존 웹의 테스트·빌드도 웹/API 계약 변경 시 실행한다.

초기 검토 결과: 현재 구현과 목표를 구분했고, 기존 데이터 이전·오프라인·지도 실패·정산·계정 범위를 포함했다. 설계 작성 이후 사용자 승인으로 단계 1·2 미리보기를 구현·검증했다. 지도·정산·동기화 등 전체 이식 완료를 의미하지 않으며, 다음 작업은 [단계 3 지도·저장·분할 실행 계획](../plans/2026-09-21-native-maps-saved-split.md)이다. 새 검색 데이터의 장기 보관 경계와 현재 웹 백업의 지도 위치 복원 한계는 이 계획에서 명시하고 검토받는다.
