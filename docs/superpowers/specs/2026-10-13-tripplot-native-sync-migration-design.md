## 1. 목표와 성공 기준

현재 웹 계정의 여행·저장 장소 데이터를 보존하면서 iOS SwiftUI 앱과 웹이 같은 계정 데이터를 양방향으로 사용할 수 있는 공통 저장·동기화 기반을 만든다. 각 화면의 구현은 뒤따르는 하위 작업에서 진행한다.

완료는 다음을 모두 확인했을 때로 정의한다.

- 웹에서 만든 여행과 저장 장소가 iOS 로컬 저장소에 내려오고, iOS에서 수정한 내용이 웹에 반영된다.
- 인터넷이 끊겨도 기기에 저장한 변경을 잃지 않으며, 재연결 후 중복 없이 동기화한다.
- 오래된 앱/웹 탭의 동시 편집, 계정 전환, 삭제, 부분 실패가 조용한 덮어쓰기나 데이터 부활을 만들지 않는다.
- 이전에 실패하거나 앱이 종료되어도 원본 데이터가 남고 같은 이전을 안전하게 재시도할 수 있다.
- 기존 운영 앱은 네이티브 동기화와 데이터 이전 검증이 끝날 때까지 교체하지 않는다.

## 2. 승인된 제품 범위와 현재 구현

장기 목표는 iOS SwiftUI 앱의 주요 메뉴와 기능을 웹과 동등하게 제공하는 것이다. 기준 하단 메뉴는 `내 여행 / 저장 / 예산·지출 / 여행 기록 / 더보기` 다섯 개이며, 지도는 별도 하단 메뉴가 아니라 선택한 여행의 일정 화면과 연결한다. 기능·정보 구조의 동등성을 우선하고, iOS의 안전 영역과 기본 조작 방식은 유지한다.

이번 문서는 동기화와 이전만 설계한다. 기존 대화에서 승인한 기능 이관 순서는 공통 데이터 기반 → 여행·일정·지도 → 저장 장소 → 예산·지출·정산 → 기록·사진·더보기다. 지도 키가 없어도 이 기반 및 다른 기능은 진행할 수 있고, 지도 제공자 실연동 검증은 키를 설정한 뒤 수행한다.

현재 코드에서 확인한 기준:

| 영역 | 현재 상태 | 설계상 의미 |
| --- | --- | --- |
| 배포 iOS 앱 | `com.travelplaner.app` 번들의 `TravelPlaner`가 운영 웹을 `WKWebView`로 표시 | 동일 앱 업데이트와 기존 웹 저장소 이전을 검증하기 전에는 이 앱을 대체하지 않는다. |
| SwiftUI 앱 | 별도 미리보기 타깃이 `NativeCore.TripRepository`로 SQLite/Core Data 저장, 사진은 앱 파일 저장소 사용 | 로컬 데이터 형식은 웹의 브라우저 저장소와 별개이며 기존 미리보기 데이터를 보존해야 한다. |
| 웹 계정 동기화 | Supabase `user_state(user_id, key, value)`에 `world_pro_trips_v1`, `world_pro_fav_v1` 배열을 저장 | 배열 전체 `upsert`는 동시 편집에서 오래된 배열이 다른 변경을 덮을 수 있다. 이 키들은 v1 이전 자료로 취급한다. |
| 공유 여행 | `/api/shared-trips` 서버 경유 API와 별도 소유자/관리 권한이 있음 | 공유 링크·권한 모델을 우회하지 않고 호환되는 동기화 어댑터를 둔다. |

## 3. 선택한 구조

### 3.1 로컬 우선 클라이언트

iOS는 기존 `NativeCore` 저장소를 기반으로 로컬에 먼저 저장한다. UI는 로컬 저장 완료와 서버 동기화 완료를 별개의 상태로 보여준다. 네트워크 호출은 화면에서 직접 하지 않고 `SyncRepository` 인터페이스 뒤에 둔다. 웹도 동일한 서버 계약을 호출하도록 전환한다.

각 로컬 변경은 계정·레코드별 대기열에 기록하고, 연결이 복구되면 재시도한다. 로그아웃·계정 전환 시 한 계정의 대기 변경을 다른 계정에 올리지 않는다. 비로그인 여행은 로그인 사용자의 클라우드 데이터와 분리하고, 로그인 뒤에는 개수와 충돌을 보여주는 병합 미리보기를 거친다.

iOS는 웹과 같은 Supabase Auth 프로젝트와 사용자 ID를 사용하되, 인증 토큰은 Keychain에 보관하고 WebView 쿠키와 공유하지 않는다. 따라서 같은 계정 데이터는 이어 쓸 수 있지만 네이티브 앱에서 최초 1회 로그인이 필요하다. 계정 삭제는 현재 서버 API의 인증·삭제 순서를 재사용한다.

### 3.2 버전 2 서버 계약

Supabase Postgres에 사용자 소유의 `user_sync_records` 레코드 저장소를 추가한다. 한 레코드는 여행 문서 또는 저장 장소 한 건이다. 여행의 현재 웹 JSON 구조는 `payload`에 보존해 기존 계산 규칙 및 아직 네이티브가 편집하지 않는 필드도 왕복 중 제거되지 않게 한다.

각 레코드는 최소한 다음 값을 가진다.

| 필드 | 목적 |
| --- | --- |
| `user_id`, `record_type`, `record_id` | 소유자와 레코드 종류·안정 ID. 이 조합은 고유하다. |
| `payload` | 기존 웹 필드와 알 수 없는 확장 필드를 보존하는 JSON 문서. |
| `revision` | 서버가 원자적으로 증가시키는 낙관적 동시성 버전. |
| `updated_at` | 서버 기준 최종 변경 시각. 충돌에서 임의 승자를 정하는 용도로 사용하지 않는다. |
| `deleted_at` | 삭제 tombstone. 일반 클라이언트의 동기화로 자동 제거하지 않는다. |

쓰기 작업은 인증 사용자와 `expected_revision`, 고유 `operation_id`를 전달하는 서버 RPC를 사용한다. RPC는 인증 사용자 소유권을 확인하고 revision이 일치할 때만 저장한다. 테이블 직접 쓰기는 허용하지 않고 RLS로 본인 레코드만 읽게 한다. 별도 `sync_operation_receipts`의 `(user_id, operation_id)` 고유 제약으로 처리 결과를 기록하므로, 이미 처리된 operation 재요청은 중복 변경을 만들지 않는다.

초기 구현은 로그인·앱 복귀 때 사용자 레코드 전체를 페이지 단위로 읽고, 로컬 대기 작업을 revision 순서대로 올린다. 데이터 크기가 실제 측정에서 문제로 확인되기 전에는 별도 변경 스트림이나 복잡한 실시간 구독을 추가하지 않는다. 공유 여행은 기존 서비스의 폴링 갱신을 유지한다.

revision이 오래된 쓰기는 서버에서 거절하고 현재 서버 문서를 반환한다. 클라이언트는 로컬 초안과 서버 버전을 모두 복구 가능한 충돌 항목으로 보존한다. 서로 다른 필드의 자동 병합은 안전성이 입증된 필드에만 적용한다. 같은 필드가 다르면 사용자에게 양쪽 값을 비교·선택하게 하며, 선택 전에는 어느 쪽도 폐기하지 않는다.

삭제는 tombstone으로 전파한다. 초기 버전은 tombstone을 자동 정리하지 않는다. 계정 전체 삭제 같은 명시적인 데이터 수명주기 작업 외에는 삭제 이력을 없애지 않아 오래 오프라인이던 기기가 지운 여행을 다시 올리지 못하게 한다.

공유 여행은 기존 `/api/shared-trips`를 통한 권한 검사를 유지한다. 이 API도 revision 기반 수정 및 삭제 이력을 지원하도록 별도 호환 작업을 수행한다. 네이티브 앱이 `shared_trips` 테이블에 직접 접근하지 않는다.

### 3.3 사진 데이터

사진 바이너리와 여행 JSON을 분리한다. 신규 미디어는 비공개 Supabase Storage 객체로 보관하고, 여행 문서에는 안정적인 미디어 ID와 메타데이터만 둔다. 개인 미디어는 소유자 정책으로 보호한다. 공유 여행 미디어는 기존 공유 API가 멤버 권한을 검사한 뒤 읽기 권한을 부여하며, 네이티브가 버킷에 직접 접근해 공유 권한을 우회하지 않는다. 만료될 수 있는 signed URL이나 기기의 로컬 파일 경로를 동기화 문서의 기준값으로 저장하지 않는다.

기존 웹 사진 데이터 URL과 네이티브 파일은 원본을 유지한 채 대상 객체로 복사한다. 콘텐츠 형식·크기·SHA-256을 확인하고 모든 참조가 읽히는 것이 확인된 뒤에만 새 문서에서 이전 참조를 사용한다. 이전 확인 전에는 v1 원본이나 로컬 사진을 삭제하지 않는다.

## 4. 초기 동기화와 데이터 이전

동기화 초기화는 서버 스냅샷을 읽고, 로컬 데이터를 비교하고, 미리보기를 보여주고, 사용자가 병합을 확정한 뒤에만 서버 변경을 전송한다. 서버에서 데이터를 받았다는 이유만으로 로컬을 덮지 않는다.

이전 원본은 세 종류로 구분한다.

1. **웹 계정 데이터:** 기존 `user_state`의 여행·즐겨찾기 행을 읽기 전용으로 변환한다. 여행 ID와 문서 필드는 유지한다. 안정 ID가 없는 즐겨찾기는 계정·원본 항목에 결합한 결정적 매핑과 이전 영수증으로 반복 실행 시 중복을 방지한다.
2. **기존 WebView 앱의 로컬 데이터:** 같은 운영 원점의 영구 `WKWebsiteDataStore`에서 내보내는 1회성 이전 브리지를 검증한다. 이전 브리지는 저장소 읽기/내보내기만 담당하고 일반 앱 화면·네비게이션에는 사용하지 않는다. 접근·내보내기에 실패하면 원본 저장소를 건드리지 않고 JSON 백업 가져오기를 안내한다.
3. **Safari/Chrome 브라우저 전용 데이터:** 네이티브 앱이 다른 앱의 브라우저 저장소를 직접 읽을 수 있다고 가정하지 않는다. 로그인 동기화 또는 사용자가 직접 선택하는 JSON 이전 패키지를 제공한다.

이전 단계는 `원본 백업 → 형식·필수 필드 검증 → 여행/장소/지출/기록/사진 개수와 충돌 미리보기 → 사용자의 확정 → 로컬 트랜잭션 저장 → 재읽기 및 해시 비교 → 이전 영수증 기록` 순서다. 잘못된 일부 레코드는 격리하고 전체 이전 성공으로 표시하지 않는다. 네트워크 오류·앱 종료는 안전하게 재시도한다.

이전 중 생성되는 백업과 미리보기에는 비밀 공유 관리 토큰을 포함하지 않는다. v1 `user_state` 행과 웹 로컬 원본은 전환 검증이 끝나도 롤백·복구 기간 동안 읽기 전용으로 유지한다.

## 5. 웹·네이티브 전환 순서

| 순서 | 작업 | 다음 순서 전 기준 |
| --- | --- | --- |
| 1 | v2 테이블·RLS·RPC·Storage 권한을 추가한다. v1 읽기/쓰기는 아직 유지한다. | RLS, 소유권, revision 경쟁, tombstone, operation 중복 테스트 통과 |
| 2 | 웹을 v2 읽기/쓰기 및 v1 가져오기 지원으로 배포한다. 기존 데이터를 읽고 v2에 이관하되 v1 원본은 보존한다. | 테스트 계정에서 웹 기능과 v1→v2 재시도/복구 검증 |
| 3 | 실제 SwiftUI 앱에 인증·로컬 대기열·v2 어댑터를 연결한다. 미리보기 타깃은 개발/검증용으로 유지한다. | 웹↔iOS 양방향 편집과 오프라인 재연결 검증 |
| 4 | 모든 새 클라이언트가 v2를 사용함을 확인한 뒤 v1 쓰기를 차단한다. 구버전은 로컬 데이터를 보존하고 새 버전으로 갱신하라는 안내를 보여준다. | 구버전의 오래된 쓰기가 서버 자료를 덮지 않고 새 버전에서 복구 가능 |
| 5 | 네이티브 화면별 기능 검증과 사용자 데이터 이전 검증 후 실제 앱의 기본 실행 화면을 SwiftUI로 전환한다. | 기존 앱 업데이트 데이터 보존, 복구 경로, 핵심 기능 체크리스트 완료 |

v1 쓰기 차단은 v2 웹 배포보다 먼저 하지 않는다. 이전 데이터 해시/개수 불일치, 권한 누수, 공유 여행 손실이 하나라도 발견되면 다음 단계로 넘어가지 않고 v1 원본에서 복구한다.

## 6. 오류 및 복구 동작

- **오프라인:** 로컬 저장은 계속 가능하고 동기화는 `대기 중`으로 표시한다. operation ID로 재시도해 중복을 막는다.
- **로그인 만료:** 대기 변경은 해당 계정에 보존하고 다시 인증할 때까지 다른 계정으로 보내지 않는다.
- **revision 충돌:** 양쪽 문서와 원본 revision을 복구 가능한 충돌 목록에 둔다. 시간만 비교해 자동 덮어쓰지 않는다.
- **부분 이전 실패:** 성공·실패 레코드를 구분해 알리고 미완료 항목을 재시도한다. 원본 v1과 로컬 파일은 유지한다.
- **권한 오류:** 공유 여행 접근 불가와 개인 계정 로그인 오류를 구분하고, 권한이 없는 데이터는 캐시 공유·업로드하지 않는다.
- **저장소/서버 장애:** 로컬 저장 실패는 성공으로 표시하지 않는다. 서버 장애 시 로컬을 유지하고 재시도 가능 상태를 보여준다.
- **계정 전환:** 계정별 로컬 범위를 분리한다. 다른 계정의 사용자 데이터가 새 계정으로 자동 업로드되지 않는다.

## 7. 검증 기준

### 자동 검증

- 계약 fixture로 웹과 Swift 변환 결과의 필드·금액·날짜·ID 보존을 비교한다.
- RPC의 본인/타인 접근, 같은 `expected_revision` 동시 쓰기, operation 재전송, 삭제·재생성 사례를 테스트한다.
- 마이그레이션을 두 번 실행해도 문서와 미디어가 중복되지 않는지 확인한다.
- 저장 도중 강제 실패, 손상 JSON, 존재하지 않는 미디어, 앱 종료 후 재시도에서 원본을 보존한다.

### 수용 테스트

1. 웹에서 여행·저장 장소·사진을 만들고 SwiftUI 앱에서 같은 계정으로 확인한다.
2. iOS에서 일정을 수정·삭제하고 웹에서 반영 및 삭제 유지 여부를 확인한다.
3. 두 클라이언트에서 같은 여행을 오프라인/온라인으로 동시에 수정해 충돌 복구와 사용자 선택을 확인한다.
4. 네트워크 차단 상태에서 변경 후 앱을 종료·재실행하고 연결을 복구해 중복·누락 없이 동기화한다.
5. 로그인/로그아웃/계정 전환, 공유 링크 권한 만료, 계정 삭제 후 다른 데이터가 노출되지 않는지 확인한다.
6. 기존 iOS 앱 업데이트, WebView 로컬 저장소 이전, 사진 이전을 각각 실제 설치 데이터로 검증한다.

웹·네이티브 계정 간 왕복 수용 테스트와 기존 설치 데이터 이전이 통과하기 전에는 동기화 또는 네이티브 전환이 완료됐다고 표시하지 않는다.

## 8. 하위 작업 분해 및 범위 제외

이 프로젝트는 여러 독립 기능 영역이므로 한 번에 구현하지 않는다. 이 문서는 아래 첫 번째 작업만 정의한다.

1. **공통 동기화·이전 기반 — 이 문서의 범위.** v2 계약, 웹 호환 전환, Swift 동기화 어댑터, 안전한 v1 가져오기.
2. **SwiftUI 여행·일정 작업공간.** 5개 탭과 여행 선택 상태, 일정 편집 및 지도-일정 분할.
3. **지도·저장 장소.** 검색, 위치 권한, Google API 키와 즐겨찾기 이식.
4. **예산·지출·정산.** 기존 계산 규칙을 공통 fixture로 검증하며 네이티브 UI를 이식.
5. **여행 기록·준비·더보기.** 사진, 준비 체크리스트, 계정·백업·지원 기능.
6. **실제 앱 전환.** 앱 업데이트·서명·복구·실기기 검증 후 WKWebView 본문 제거.

각 기능 영역은 구현 전에 자체 범위·테스트 계획을 가진 설계/계획을 별도로 승인받는다. 이 문서만으로 UI 전체 구현이나 운영 DB 변경을 시작하지 않는다. Android 구현, 신규 LLM 서비스, 오프라인 지도 타일 저장은 이 문서의 범위가 아니다.

## 9. 사용자 검토 항목

- v2 동기화의 개인 데이터 기준 저장소를 Supabase로 두고 웹과 SwiftUI가 같은 계약을 사용하는 방향.
- 오래된 `user_state` 데이터와 WebView 로컬 데이터를 원본 보존·미리보기 후 병합하는 방향.
- 충돌 시 시간 기준 자동 승자를 두지 않고 양쪽 버전을 보존하는 방향.
- 지도 키 입력과 지도 실연동 검증은 다른 화면/동기화 작업과 분리하는 방향.
- 이 문서를 첫 하위 작업의 설계로 확정하고, 이후 구현 계획은 이 동기화 기반만 대상으로 작성하는 방향.
